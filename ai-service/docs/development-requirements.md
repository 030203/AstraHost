# 开发需求与优先级

## 1. 项目目标

`ai-service` 的目标是为 FindMyBed 民宿平台提供稳定、安全、可追踪的客服 Agent 服务。Agent 应能理解用户问题，调用平台后端工具查询真实业务数据，并以中文客服话术给出可靠回复。

## 2. 当前范围

当前已覆盖的业务范围：

- 房源和房型咨询。
- 订单查询和订单动作。
- 支付记录查询。
- 评价查询和评价回复。
- 通知查询和已读状态更新。
- 优惠券查询。
- 商家和用户信息查询。
- 天气和外部搜索。

## 3. P0 需求

P0 是上线前必须优先处理的稳定性和安全需求。

### 3.1 写操作二次确认

所有 action 工具必须先生成待确认动作，不允许模型在用户含糊表达下直接执行。

涉及工具：

- `cancel_booking`
- `check_in_booking`
- `check_out_booking`
- `reply_review`
- `mark_notification_read`
- `mark_all_notifications_read`

验收标准：

- 用户问“能不能取消订单”时，不执行取消。
- 用户明确“确认取消订单 XXX”后，才允许执行。
- 执行前重新读取资源详情并校验归属和状态。

### 3.2 可信身份来源

后端不能把前端传入的 `role`、`id`、`merchantId` 作为生产权限依据。

验收标准：

- 生产环境身份来自认证 token 或服务端 session。
- mock userContext 只能在开发模式启用。
- 普通用户不能通过伪造 `ADMIN` 角色访问管理工具。

### 3.3 真实会话状态

`conversationId` 必须能关联后端会话历史。

验收标准：

- 用户可以连续追问同一订单、房源或支付记录。
- 会话历史有 TTL。
- 工具结果只保留必要摘要，避免上下文膨胀。

### 3.4 fallback 工具收敛

未命中明确技能时，不应暴露当前角色下全部读工具。

验收标准：

- 未命中时只开放低风险工具。
- 涉及身份数据但信息不足时先追问。
- 工具暴露列表可在日志中追踪。

### 3.5 权限和路由测试

需要建立最小自动化测试集合。

验收标准：

- 覆盖 USER、MERCHANT、ADMIN 和匿名用户。
- 覆盖订单、支付、通知、评价权限判断。
- 覆盖关键 skill 路由和 fallback 行为。

## 4. P1 需求

P1 是体验和可观测性增强。

- 真正的模型流式输出。
- 工具调用过程 SSE 事件。
- 结构化错误类型和客服话术。
- 结构化日志和基础指标。
- 模型意图分类兜底。

## 5. P2 需求

P2 是长期维护和扩展能力。

- prompt 文件化和版本管理。
- 前端展示 route、tool 和 requestId。
- FAQ/RAG 知识库。
- 后台运营配置化。

## 6. 非目标

当前阶段不做以下事情：

- 不一次性重写为 LangChain 或 LangGraph。
- 不引入复杂多 Agent 编排。
- 不重构全部后端 API。
- 不做大规模前端改版。
