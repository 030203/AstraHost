# Agent 设计规范

## 1. 设计原则

客服 Agent 的核心分工：

- 模型负责理解问题、组织话术和解释结果。
- 工具负责查询或修改真实业务数据。
- 权限层负责判断用户能不能访问或修改资源。
- 日志和测试负责让行为可追踪、可回归。

## 2. 回复标准

默认中文回复，优先采用以下结构：

```text
结论
关键依据
下一步建议
```

涉及平台真实数据时：

- 必须基于工具结果回答。
- 不编造订单状态、支付状态、价格、库存、评价数量。
- 工具失败时说明无法完成查询，并给出可执行建议。

## 3. 多轮对话标准

Agent 应保存并使用以下上下文字段：

- 最近讨论的订单号或订单 ID。
- 最近讨论的房源 ID、房型 ID、城市、价格范围。
- 最近讨论的支付单号。
- 最近讨论的评价 ID。
- 用户偏好，例如亲子、老人同行、预算、交通、设施。

长期不需要保存：

- 完整工具响应。
- 敏感个人信息。
- 密钥或 token。

## 4. 意图路由标准

路由应优先稳定、可解释。

推荐层级：

1. 明确规则和关键词。
2. 业务编号格式识别。
3. 模型结构化分类。
4. 低风险 fallback。

当置信度低时，Agent 应追问，而不是猜测调用敏感工具。

## 5. 工具选择标准

- 公开咨询优先使用房源、房型、搜索、天气等低风险工具。
- 身份相关问题必须先确认用户已登录且身份可信。
- 订单、支付、通知等数据必须经过权限过滤。
- 不把无关工具暴露给模型。

## 6. 写操作标准

写操作必须经过二次确认。

标准流程：

```text
用户提出动作
  -> 查询目标资源
  -> 展示动作影响
  -> 用户明确确认
  -> 执行前重新校验资源状态和归属
  -> 执行动作
  -> 返回结果并记录日志
```

明确确认语句示例：

```text
确认取消订单 BOOK20250401001
确认将通知 123 标记为已读
确认回复评价 456：感谢您的反馈
```

## 7. 前端体验标准

控制台应尽量展示可调试信息：

- conversationId。
- requestId。
- 命中 skill。
- 调用工具。
- 工具调用状态。
- 错误类型。

但不应展示敏感数据、密钥或完整内部异常堆栈。

## 8. 安全边界

以下行为禁止：

- 仅凭用户口头声明切换成 ADMIN。
- 根据前端伪造 merchantId 查询商家数据。
- 在未确认时执行取消订单、入住、离店、评价回复、通知已读。
- 把工具错误直接作为最终客服答案。
- 在日志中记录密钥、token 或完整隐私数据。
